この画面を動かしている実データ

すべて ODPT の公開データから算出。固定値の埋め込みはありません。

2つのデータを繋いで初めて出せるもの

単独のフィードでは絶対に作れない部分。

運休日の代替手段 2データ結合 デマンド交通は木曜・日曜が運休（calendar.txt）。 一方コミュニティバスはその日も走る。両方のカレンダーを突き合わせて、 運休日には自動でバス経路に切り替える。利用者が押すボタンは同じ。 手段はアプリが選ぶ。
予約締切の逆算 3データ結合 「この電車に乗るには10時32分までに予約」——この数字は booking_rules.prior_notice_duration_min（30分前）、 JR八高線の発車時刻、乗降場と駅の座標から出した所要時間の 3つが揃って初めて出る。単独のフィードでは絶対に書けない。
接続点 2データ結合 箱根ケ崎駅を3つのフィードが共有する。デマンド交通の乗降場（東口・西口）、 バス停、JRの駅がそれぞれ別IDで別データにあり、座標で突き合わせている。 ここで町内の「点」が町外への「線」になる。

データが埋まれば、ここまで届く

現状の制約と、その原因。

ワンタップ予約確定 未提供 booking_rules.booking_url が空。 message には「オンライン予約は24時間受付」とあるが URL がデータに無いため、 アプリは電話発信までしか到達できない。1フィールド埋まるだけで予約まで繋がる。
列車の遅延反映 未実装 使っているのは静的な時刻表。ODPT には JR東日本の列車ロケーション情報もあるので、遅延を予約締切の逆算に反映できる。 「電車が5分遅れているので、あと5分予約を待てます」まで出せる。
車椅子で乗れるか データに無い 3フィードのいずれにも記載がない。デマンド交通とコミュニティバスは wheelchair_boarding / wheelchair_accessible の 列そのものが無く、JR東日本は列はあるが772駅・18,520便すべて空欄。 バリアフリーは本チャレンジの募集テーマの一つだが、判定できるデータが無い。 そのため本アプリは利用者の設定として持ち、所要時間に反映したうえで、 配車の可否は電話で確認してもらう案内に留めている。
乗車・到着の検知 層が違う GTFS-Flex は静的な運行定義で、 乗降のイベントは含まれない。個人の乗降状態は事業者の配車システムにしかなく、 GTFS-RT を足しても分かるのは車両位置まで。そこで本アプリはお迎え時刻＋3分で乗車とみなし、 到着時刻は乗降場の座標から概算している。

デモ用：日時を変える

木曜・日曜を選ぶと、デマンド交通が運休しバスに切り替わります。空欄で実時刻。
実時刻ならお迎え時刻＋3分で乗車、概算所要時間で到着へ進みます。 仮想日時では時計が止まるため、代わりに10秒ずつで進めます。
